# dds-profile-qualified-bc

DDS profile (differential + generated snapshot + generated JSON Schema)
expressing a qualified (sibling) biomedical concept per
`../dds_base/PROFILING_SPECIFICATION.md` v0.1.0.

- `profile.yaml` — the differential (source of truth).
- `snapshot.yaml` — generated by `../dds_base/dds_profile_snapshot.py`;
  never hand-edited.
- `qualified-bc.schema.json` — `gen-json-schema --closed --top-class
  MetaDataVersion` over the snapshot.

Design, in one paragraph: identity, typed external codings and the
thinned recording project onto BASE slots (OID-as-IRI, coding with
AliasPredicate's skos semantics, ItemGroup/Item with
`Item.conceptProperty`). The profile TIGHTENS ReifiedConcept (OID and
coding required) and adds five declared, optional, strippable
extensions: ddsqResultScale (enum mirroring COSMoS result scales),
ddsqBroaderConcept, ddsqInterpretationRegimes (extension class),
ddsqDataType and ddsqSemanticValueSet on ConceptProperty.
The ONE base-model ask is ConceptProperty.dataType — see the header of
`profile.yaml`. MetaDataVersion is untouched: concept-library
containment/transport is a base-model question.

Findings against their tooling (2026-08-29, repo pinned at d2328345):
- The base model has no `version:` field, so the spec's R1 version gate
  cannot bind; snapshot runs with `--allow-unversioned-base` and the
  commit pin lives in `dds.profile.baseVersion`.
- Their resolver enforces the strict reading of spec §5: extension
  slots MUST be optional (required extensions are a resolution error).
  ddsqResultScale/ddsqDataType are therefore `recommended`, not
  required — which is itself the argument for absorbing dataType into
  base, where `required` would be legitimate.

Validation: `python3 ../validate_dds.py` — 13 checks: own instance
(base + profiled + stripped), all code lists, the recording, the
engine's CONC.BiomedicalConcept_55 against base AND profile, and three
negative controls proving the tightening bites.
