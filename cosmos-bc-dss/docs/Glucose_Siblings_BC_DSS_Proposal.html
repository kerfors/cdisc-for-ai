Glucose siblings: specify on the BC, not the DSS

A worked design for lifting the qualified-measurement distinctions out of the Dataset Specialization layer and into referable Biomedical Concepts — the identifier question (#1), the value-type & reference-range question (#2), and the most feasible way to build a first proof.

Grounded in COSMoS package 2026-05-26 · SDTM CT (NCI EVS) 2026-03-27 · every C-code below is real, pulled from the package.
Status: draft for discussion / analysis artifact — a proposed direction, not a standards deliverable.

The problem in one line

Langendorf's rule: the moment a specialization has to add the clinical distinction, the BC above it was underspecified — a single-source-of-truth problem, not a storage one. Glucose is the clean case. It isn't one concept quietly fanning out into storage variants; it is several observations wearing one name. A plasma glucose is a quantity; a urine dipstick is a category. Those aren't storage aisles, they're different animals — the result type is the heart of the observation, not a filing detail.

Applied here: the distinctions belong up in sibling BCs, inherited once — not curated downstream across CDASH, SDTM and ADaM.

What the package actually shows

Today there is exactly one glucose-measurement BC, C105585, with eight DSS siblings hanging off it. Every distinguishing attribute — specimen, result scale, method — is pinned inside the DSS as an assigned term. The BC's result_scales is the union Quantitative;Ordinal, so a composite pointing at the parent cannot tell which sibling is which. Reference range is modelled nowhere — not on the BC, not in the DSS template.

What CDISC's own guidance says

Two authoring files from the COSMoS starter package bear on this, and they rank differently. The BC Curation Principles & Completion Guidelines is normative prose ("must" / "should", governance-reviewed) — high credibility. The BC DEC Templates is a working scaffold of default DEC sets, with duplicated rows and defaults the live package overrides — treat as illustration only.

The granularity rule (high-credibility) is a storage criterion. The Principles set how finely to split a Dataset Specialization by aggregability in a regulatory submission: "split … based on the biomedical specimen and/or method when it is motivated by analysis and reporting. Tests that can be integrated during analysis and reporting, e.g., serum, plasma, or blood … would not be split, while … urine glucose and blood glucose" are separate. So CDISC's own rule sets granularity by how data pools for reporting — precisely the storage-driven basis that "specify on the BC, not the DSS" contests. It lands near our glucose split (urine separate), but for a different reason: poolability, not observation identity.
The two files collide on glucose. Poolability (Principles) would keep GLUC together; result value-type (fixed per template in the DEC scaffold — Lab = decimal) cannot hold quantitative plasma and categorical dipstick in one group. Glucose sits exactly on that fault line — which is why categorical urine glucose is awkward today, and why a result-scale sibling resolves a seam the guidance itself leaves open. The DEC-template decimal is only a weak echo — the live glucose DEC is typed string — so the weight rests on the poolability rule, not the template.

Naming, for the record: the Principles do give a vlm_group_id convention — uppercase + underscores, TESTCD + specimen (GLUCBLD, GLUCPL, SODIUMSERPL) — but explicitly as a "user-friendly identifier / primary key," i.e. a mnemonic, not a resolvable or cross-domain-unique identity. That is the gap #1 fills: the guidance governs completion, not identity.

#1The identifier: a name a composite can point at

If the distinction lives on the BC, the sibling needs a governed, cross-referenceable identifier — because a composite must point at the specific sibling, not the parent analyte. Two familiar composites make the point, and both are Activity Specifications — collection compositions that sit one layer above the BC:

  • an Oral Glucose Tolerance Test (OGTT) — bundles a glucose load with glucose readings taken across time (fasting, 60 min, 120 min); it must reference the plasma-quantitative sibling, not "glucose";
  • a lab panel — e.g. a Basic Metabolic Panel bundling glucose with sodium, potassium, chloride, BUN and creatinine on one draw; it must reference each member at the qualified grain (plasma glucose, serum sodium…), not the bare analytes.

NCIt has C105585 (the analyte); it does not enumerate "glucose, plasma, quantitative." So the sibling identity — which today exists only implicitly as the DSS mnemonic GLUCPL — has to become something explicit that both an OGTT and a panel can point at.

Not GUIDs. A GUID is right for the instance layer (this Activity in this study — where d4k uses them) but wrong for a concept. A concept id is a read-many, cited, shared name; a GUID advertises nothing and no one can recognise or check it — the mnemonic problem made worse. usdm-rdf already answered this: /Activity, readable but not parsed, semantics in the body. The sibling follows the same precedent.

Where it lands: the identity is the readable resolvable IRI (…/bc/GlucoseBloodQuantitative) — always exactly one, CDISC-owned. It carries no opaque placeholder token. Instead it anchors outward: skos:broader to the NCIt analyte C105585, and — crucially — to LOINC, which already codes this specimen×scale grain. The plasma-equivalent sibling also has a real NCIt code, C163446, added as exactMatch. GUIDs stay at the instance layer.

# the sibling, resolved as turtle — the IRI is the identity
bc:GlucoseBloodQuantitative a cosmos:BiomedicalConcept ;
    skos:prefLabel     "Glucose, blood-derived, quantitative" ;
    skos:broader       ncit:C105585 ;                 # analyte (NCIt stops here)
    skos:narrowMatch   loinc:2345-7, loinc:14749-6 ;  # unit-specific LOINC leaves (mass / molar)
    cosmos:resultScales "Quantitative" ;             # single & authoritative
    cosmos:resultDEC   ncit:C70856 ;                  # dataType inherited by every recording
    cosmos:specimenDEC ncit:C70713 ;
    cosmos:unitExampleSet "mg/dL","g/L","mmol/L" .

Using LOINC when the count is 0, 1, or more than 1

LOINC is a mapping target, not the key. The identifier stays the CDISC-owned IRI (always exactly one); LOINC attaches as a typed, multivalued skos mapping — which is exactly what SKOS mapping properties are for, so the irregular count is handled natively:

  • exactly 1 → skos:exactMatch — sibling and LOINC term denote the same observable (the dipstick cases, 25428-4, 2349-9).
  • more than 1 → the sibling abstracts over a finer LOINC split — characteristically the unit axis (mass vs molar; the sibling's own mg/dL;g/L;mmol/L recording variants) or method. Model each as skos:narrowMatch: the sibling sits above the LOINC leaves — one concept over several unit-specific realisations. Not a defect; the sibling correctly being unit-neutral.
  • 0 → identity is unaffected — the IRI and skos:broader C105585 still hold. Either the specific LOINC exists but wasn't pinned in this package (the GLUCPL / GLUCSER case — plasma- and serum-specific glucose codes do exist) and you add it, or you leave the mapping empty.
Cardinality becomes a QC lens. Because identity never depended on LOINC, 0/1/>1 stops being a problem and starts being a signal: two exactMatch codes on one sibling is a smell — either retype them to narrowMatch (unit variants) or the sibling is still too coarse and should split; zero is a coverage gap to chase. The count tells you whether your grain is right.

Caveat: the exact meaning of each paired code (mass vs molar, method) needs a LOINC lookup to confirm — the package carries the codes, not their long names.

#2Value-type & reference-range: where they live

Value-type — today it lives on the DSS variable; inherit-once is the proposal

Per the high-credibility Curation Principles, value-type is populated on the DSS result variable — "only the result variable will require population of data type, length, and format." The parent's result_scales is the union Quantitative;Ordinal, and the authoritative float-vs-text difference lands on LBORRES — curated downstream, the exact pattern the rule critiques. The BC's own DEC dataType is only loosely populated today (the live C105585 result DEC says string while the DSS says float/text), so it can't be relied on as-is.

The proposal — not an existing mechanism: split the siblings so each carries one scale, make the sibling's result DEC dataType authoritative, and let the recording inherit it through the FK that exists (SDTMVariable.dataElementConceptId → DataElementConcept.dataType) instead of re-declaring it per DSS. No new slot — but it does require making the DEC dataType the single source of truth, which today it is not.

Reference-range — modelled nowhere; separate regime from values

No normal-range variable appears in any glucose DSS, and there is no reference-range slot on the BC. The tractable move is to split the claim:

  • the fact that a distinct regime applies (plasma ≠ whole-blood ≠ urine) is conceptual → a coded pointer on the sibling BC;
  • the actual limits (numbers, age/sex-partitioned, lab-specific) are data → stay per-record.

So "reference range inherited once" means inheriting the regime pointer, never the numbers. That single pointer is also what finally adjudicates whole blood: same regime as plasma → GLUCBLD is a recording; different regime → it's a sibling.

Parked deferred — the reference-range regime pointer is the one genuinely new BC slot, and the whole-blood call waits on it. Everything else needs no schema change.

The combined solution: split by what needs CDISC

#1 and #2 are the same object — the sibling BC — seen from identity and from content. The most feasible path does everything that needs no schema change and no CDISC decision first, as an overlay + projection, and reduces the governance ask to a short list.

Stage 0 — build it yourself (free)

  • Author ~4 sibling BCs in an overlay (schema-identical; identity = readable IRI, anchored to NCIt + LOINC)
  • Value-type inherited via the DEC FK (make the DEC dataType authoritative)
  • Resolvable IRIs projected to RDF + HTML, usdm-rdf style, over w3id
  • Composites — an OGTT, a panel — can point at siblings immediately
  • Core untouched · no CDISC dependency · an existence proof

Stage 1 — the CDISC ask (the tail)

  • Adopt the siblings & own the id lifecycle (split / merge / deprecate)
  • Own the resolvable namespace (the USDM Governance Group ask, one grain deeper)
  • Add one BC slot — the reference-range regime pointer

GUIDs would make id allocation free, but not the lifecycle. Svansen sitter kvar.
